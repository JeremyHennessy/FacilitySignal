# Weekly refresh and release policy

One GitHub Actions job runs Monday 11:17 UTC (07:17 Atlantic standard time, 08:17 Atlantic daylight time) and on manual dispatch. First live run is triggered by qualified main promotion. It checks the nine Care Compare sources by exact publisher release date, URL and independent row count. For a newer release within proposed 75–125% count bounds, import only that source into isolated SQLite, reconcile independent counts and checksums, validate integrity and national jurisdiction coverage, create an immutable private candidate and completion receipt under CMS Facility Demo/refresh/care-compare. If the same candidate receipt already exists, check its scope, size and audit hash rather than download it again. A same-date changed release, older date, out-of-bound count or schema failure remains blocked. No pointer overwrites. Raw CSVs discarded. Registry and ownership version discovery is metadata-only because their existing adapters and evidence are pinned; nursing penalties/dates/summaries likewise require updated source-specific qualification. NPPES weekly archives are discovered by exact official week labels and independently qualified with the organization-only streaming adapter. Reuse prior successful observations, retain only aggregate audit for new weekly releases, no raw/individual records, no monthly union or active-status inference. A new monthly release requires separate review. HCRIS annual forms, QCOR unversioned workbooks, HRSA, FDA and other sources remain source-specific workstreams pending safe refresh policies.

The public app is still GitHub Pages. This workflow does not replace its approved data packs. A second coordinated release gate must rebuild affected directory shards, source locks, service/enrichment packs, market aggregates and browser checksum expectations from one coherent version set, verify release and cross-source consistency, then publish the qualified pack set. Until that exists the weekly job is automatic acquisition/qualification and change monitoring, not automatic public data cutover. Keep the original national and extension pointers intact; no secret, private DB, source row or raw archive in Pages or public artifacts. First run and eventual scheduled execution need separate evidence. Azure existing storage and transaction costs may apply; no new resources. Coordinate with the existing custodian rather than create a competing ingestion automation.

Update: new NPPES weekly releases now persist the same Type 2-only private projection used in historical source migration, under exact source SHA. The weekly metadata index stores only its archive reference and aggregate observations, so a previously completed weekly candidate avoids another download. Legacy aggregate-only identities are not mistaken for private projections. The source observer now flushes at end of stream for releases without a prior count pin, retaining the same structural gates and checks. Candidate inventory checks before receipt creation are also enforced. Monthly replacement remains separately reviewed. No changes to public UI or application packs.
