# FacilitySignal private Azure archive bootstrap

Authorized destination: existing storage account pharm3r, container data, exact Blob folder prefix `CMS Facility Demo`. GitHub environment `azure-production`; use variables AZURE_STORAGE_ACCOUNT, AZURE_STORAGE_CONTAINER, AZURE_STORAGE_PREFIX, and secret AZURE_STORAGE_KEY. This interpretation assumes CMS Facility Demo is a Blob prefix within data; mismatched values fail before writes. No new storage resource, public access change, SAS token, or TowerSignal path mutation.

GitHub Pages remains the deployment. The archive is a private, versioned backend data snapshot, not a browser-accessible database or dynamic API. Initial scope: all 19 qualified pinned integrated sources (1,904,060 retained records) and existing qualified capability/status/identity observations, plus repository-tracked web/research JSON evidence packs. The raw original source files, excluded individual-owner records, and unintegrated/ephemeral source families are not archived in this initial release. Future source-specific private raw retention requires data reuse/privacy review; do not treat normalized snapshot as a complete raw-data archive.

The guarded initial workflow runs on trusted main and uses the environment credential only for Blob operations. On the research branch, only offline qualification runs. It fails if container access is public, configuration is wrong, or a current national pointer exists. It creates a unique probe, confirms its exact bytes, conditionally deletes only its own ETag, and verifies absence. Reconstruct exact source pins once; validate source, database, and derived counts. Upload create-only versioned payloads, stream every byte back for SHA-256 verification, reconcile exact inventory and ETags, then write a verified completion receipt and create-only national-current pointer. Failed releases remain unpromoted; no automated deletion of production data. A later refresh/promotion mechanism needs separate conditional-pointer qualification.

Actual authenticated probe, reconstruction, readback, and receipt are required before claiming durable storage. No new UI or deployment changes, nor cost/capacity confirmation from offline tests. Azure storage and transaction charges may apply to existing resources.
