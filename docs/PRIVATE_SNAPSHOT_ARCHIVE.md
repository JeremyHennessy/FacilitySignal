## Offline backup capability

The prior 19-source reconstruction is logical recovery, not byte-identical archival backup. New standalone utility accepts a **closed**, already qualified recovery output (exact database and recovery audit only) and an independently trusted SHA-256 of that audit. It checks byte length, checksum, SQLite integrity and foreign keys, rejects sidecars, symlinks, unsafe archive members, oversized payloads, pre-existing destinations and repository storage. Requires existing owner-only POSIX directories and explicit authorized-private-storage acknowledgement. ZIP stored only, no compression/decompression expansion, no raw files, network, or public uploads. A complete verified archive is published via a no-clobber hard link; restore requires both externally trusted audit and archive hashes. Restored files are byte-identical to the input, not regenerated. New restore directory is exclusive; recovery audit is placed last as readiness marker, not a live deployment pointer. An interrupted restore may leave an incomplete directory; do not serve it. Source must be quiescent, not a live database; this tool is not an authenticator, encryption system, remote storage or a substitute for release qualification. Private storage operator must verify path, ownership, access, encryption at rest and reuse permissions. The trusted audit and archive hashes must be stored independently on approved storage. No storage provisioned.

Example (only on approved existing private storage, with directories already created mode 0700):
`python private_snapshot_archive.py backup --source /private/qualified --destination /private/archive/snapshot.zip --trusted-audit-sha256 <trusted audit hash> --authorized-private-storage`

`python private_snapshot_archive.py restore --source /private/archive/snapshot.zip --destination /private/restore/new-snapshot --trusted-audit-sha256 <trusted audit hash> --trusted-archive-sha256 <trusted archive hash> --authorized-private-storage`
